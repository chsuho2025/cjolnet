## 프로젝트 결과

프롬뱅크는 생성형 AI 사용자가 잘 작동한 프롬프트와 결과, 원하는 결과에 도달하기까지의 수정 과정을 공유하는 플랫폼입니다. `PROM.ai`라는 프롬프트 연구 학회 활동 안에서 문제를 발견하고, 서비스 기획과 프롬프트 콘텐츠 제작을 담당해 실제 사용자가 탐색할 수 있는 형태로 운영했습니다.

학회 활동은 2024년 3월부터 2025년 6월까지 이어졌습니다. 그중 프롬뱅크의 콘텐츠를 집중적으로 축적한 2024년 9월부터 2025년 1월까지 5개월 동안 422개의 프롬프트 템플릿을 정리했습니다. 단과대학을 대상으로 공개한 MVP는 ==첫 4주 동안 고유 방문자 1,311명, 방문 세션 3,285회==, 평균 세션 시간 2분 55초를 기록했습니다.

숫자보다 중요하게 본 것은 한 번의 성공 결과를 다른 사람이 다시 쓸 수 있는 제작 지식으로 바꾸는 방법이었습니다. 이미지·영상·TTS·사운드 생성에서 반복되는 실패를 수집하고, `사용 목적`, `사용자가 바꿀 정보`, `유지해야 할 조건`, `결과와 수정 기록`으로 나누었습니다.

> **프로젝트를 한 문장으로 정리하면**
>
> 프롬프트 문장을 많이 모으는 서비스가 아니라, 어떤 조건 때문에 결과가 달라졌는지 다른 제작자가 이해하고 자기 장면에 맞게 다시 실행할 수 있도록 만드는 서비스였습니다.

---

## 1. 문제 정의: 정보량보다 접근 방식

생성형 AI가 빠르게 확산되던 시기, 미디어 전공생들도 이미지·영상·음성 생성 도구에 관심을 보였습니다. 그러나 수업과 학회에서 결과를 살펴보면 도구를 한두 번 체험한 뒤 최종 콘텐츠 제작에는 사용하지 않는 경우가 많았습니다.

초기에는 사용법 교육이 부족한 문제라고 생각했습니다. 인터뷰를 이어가자 기본 버튼이나 메뉴를 몰라서 멈추는 경우보다, 자신이 만들려는 장면에 어떤 정보를 입력해야 하는지 몰라 반복 생성하는 경우가 더 자주 보였습니다.

원하는 결과가 나오지 않으면 프롬프트를 조금씩 바꾸었지만, 무엇을 바꾸었고 결과가 왜 달라졌는지는 기록하지 않았습니다. 한 번 성공한 문장은 개인 메모나 대화 기록에 남았고, 시간이 지나거나 다른 사람이 사용하면 원래의 맥락을 알기 어려웠습니다.

![PROM.ai 기획서에서 정리한 정보량과 접근성의 문제](assets/projects/prombank/problem-definition.jpg)

원본 기획서에서는 문제를 `정보의 양이 부족하다`, `정보에 도달하기 어렵다`, `질문의 질이 응답 품질을 결정한다`는 세 문장으로 정리했습니다. 여기서 정보는 도구의 기능뿐 아니라 실제 제작 목적, 사용한 입력, 결과 예시와 수정 과정을 포함합니다.

> **초기 인터뷰에서 반복된 상황**
>
> **사용자**
> “영화 같은 이미지를 만들고 싶은데, 프롬프트 예시를 그대로 넣어도 제가 원하는 장면은 나오지 않아요.”
>
> **확인한 문제**
> 예시 문장에는 원래 장면의 인물·구도·조명과 출력 조건이 섞여 있었고, 사용자는 무엇을 자기 작업에 맞게 바꿔야 하는지 알기 어려웠습니다.
>
> **문제 재정의**
> 좋은 프롬프트를 찾는 문제에서, 좋은 결과를 만든 조건을 이해하고 필요한 부분만 바꾸는 문제로 범위를 넓혔습니다.

### `프롬프트를 잘 쓰지 못한다`고 정의하지 않은 이유

사용자 역량의 부족으로 문제를 설명하면 해결책은 더 많은 교육 자료를 제공하는 쪽으로만 좁아집니다. 하지만 실제 제작에서는 같은 프롬프트도 모델, 입력 이미지, 장면의 목적과 출력 길이에 따라 결과가 달라집니다.

따라서 완성 문장을 정답처럼 제공하기보다 다음 질문에 답할 수 있어야 한다고 보았습니다.

- 이 프롬프트는 어떤 제작 목적에서 사용됐는가
- 사용자가 자기 작업에 맞게 바꿀 항목은 무엇인가
- 결과를 유지하기 위해 바꾸면 안 되는 조건은 무엇인가
- 첫 결과에서 어떤 문제가 있었는가
- 다음 시도에서는 어느 조건을 수정했는가
- 생성 뒤 사람이 다시 확인해야 할 항목은 무엇인가

이 질문은 이후 카카오엔터테인먼트 숏애니 제작에서 입력 조건과 품질 기준을 기록하고, AI 드라마에서 캐릭터·공간·구도 팩을 만드는 출발점이 됐습니다.

## 2. 목표 설정: 기존 지식을 배우고 새로운 사례를 축적하는 구조

원본 기획서에서는 서비스를 두 개의 학습 흐름으로 나누었습니다.

첫 번째는 기존 지식을 효율적으로 배우는 흐름입니다. 사용자가 실제 결과에 기반한 프롬프트 템플릿을 보고, 반복 학습과 단계별 설명을 통해 자신의 작업에 적용하는 과정입니다.

두 번째는 새로운 사례를 공동으로 축적하는 흐름입니다. 사용자들이 성공 결과뿐 아니라 시행착오와 수정 근거를 공유하고, 새로운 도구와 제작 방식이 등장할 때 기존 분류에 다시 연결하는 과정입니다.

![프롬프트 교육과 커뮤니티를 생산성·지식 확장으로 연결한 초기 목표](assets/projects/prombank/goal-structure.jpg)

| 목표 | 서비스에서 제공할 경험 | 기대한 변화 |
|---|---|---|
| 기존 지식 공유 | 실제 결과와 함께 보는 프롬프트 템플릿 | 시행착오를 처음부터 반복하지 않음 |
| 단계 학습 | 넓은 요청을 역할·맥락·조건·예시로 분해 | 무엇을 수정해야 하는지 이해 |
| 사례 수집 | 사용자 작업의 성공·실패와 수정 기록 공유 | 새로운 도구의 활용 지식 축적 |
| 목적별 탐색 | 비즈니스·교육·창작과 콘텐츠 요소별 분류 | 자신의 작업에 가까운 사례에 빠르게 접근 |

> **초기 서비스 가설**
>
> 기존 지식을 일방적으로 전달하는 자료실만으로는 새로운 생성 도구의 변화를 따라가기 어렵습니다. 반대로 자유 게시판만 만들면 맥락과 검증 기준이 다른 프롬프트가 섞일 수 있습니다.
>
> 그래서 `구조화된 템플릿`과 `사용자 사례가 다시 들어오는 커뮤니티`가 함께 있어야 한다고 판단했습니다.

사용자가 자기 목적에 맞는 조건을 선택하고, 결과를 확인한 뒤 다시 수정할 수 있도록 질문의 구조를 보여주는 데 초점을 맞췄습니다.

## 3. 서비스 구조: 뉴스, 프롬프트 팁과 포럼을 한 흐름으로 연결했습니다

프로토타입의 홈 화면은 `검색`, `하이라이트`, `뉴스 업데이트`, `프롬프트 팁`, `포럼`으로 구성했습니다. 새로운 모델과 기능이 자주 등장하는 상황에서 사용자가 먼저 변화를 파악하고, 그다음 실제 활용 방법을 확인하고, 마지막으로 자신의 사례를 공유하는 흐름입니다.

![뉴스와 활용 사례를 함께 보여주는 프롬뱅크 홈 화면 프로토타입](assets/projects/prombank/prototype-home.jpg)

### 뉴스 업데이트

모델 출시, 기능 변경과 생성형 AI 이슈를 짧게 정리하는 영역입니다. 특정 프롬프트가 이전과 다르게 작동하는 이유가 모델 업데이트나 정책 변화일 수 있기 때문에, 템플릿과 도구 맥락을 분리하지 않았습니다.

뉴스를 단순히 많이 제공하는 것보다 사용자가 자신의 작업과 관련된 변화를 판단할 수 있도록 다음 내용을 함께 전달하는 것을 목표로 했습니다.

- 어떤 모델이나 기능이 바뀌었는가
- 이미지·영상·텍스트·음성 제작 중 어디에 영향을 주는가
- 기존 템플릿을 그대로 사용해도 되는가
- 새 기능을 사용할 때 추가로 확인할 위험은 무엇인가

### 프롬프트 팁

실제 작업 목적을 기준으로 프롬프트 작성 구조와 결과를 설명하는 핵심 콘텐츠입니다. 도구명만으로 분류하지 않고 `글쓰기`, `이미지`, `영상`, `음악`, `마케팅`, `교육`처럼 사용자가 해결하려는 작업과 연결했습니다.

### 포럼

플랫폼이 준비한 콘텐츠만 제공하면 사례가 제작자의 실제 문제보다 늦어질 수 있습니다. 포럼은 사용자가 새 도구를 사용하며 발견한 조건과 결과를 공유하고, 기존 템플릿과 다른 활용 방식을 제안하는 영역으로 기획했습니다.

> **정보 구조를 정할 때 사용한 질문**
>
> **뉴스만 있다면**
> 사용자는 새 기능이 나왔다는 사실은 알지만 자기 작업에서 어떻게 쓸지 알기 어렵습니다.
>
> **프롬프트 문장만 있다면**
> 어떤 버전과 상황에서 만들어진 결과인지 판단하기 어렵습니다.
>
> **자유 게시판만 있다면**
> 서로 다른 목적과 품질의 사례가 섞여 비교하기 어렵습니다.
>
> 세 영역을 연결해 변화의 맥락, 적용 방법과 새로운 사례가 순환하도록 설계했습니다.

## 4. 콘텐츠 분류: 도구가 아니라 제작 목적에서 출발했습니다

초기 프롬프트 팁에는 GPT-4o, GPT-4, 삼성 가우스, Gemini, Sora와 Udio처럼 당시 관심이 높았던 도구의 활용 사례를 배치했습니다. 다만 콘텐츠 제목은 모델 소개보다 사용자가 해결하려는 과업을 먼저 드러내도록 구성했습니다.

![GPT·Gemini 등 텍스트 작업 사례를 배치한 프롬프트 팁 프로토타입](assets/projects/prombank/prototype-tips-top.jpg)

예를 들어 다음과 같이 제목만 보고도 어떤 작업을 다루는지 알 수 있게 했습니다.

- GPT-4o: 페르소나 설정, 명확한 요청과 예시를 포함하는 방법
- GPT-4: 요약 요청, 단계별 지시와 반복 학습을 활용하는 글쓰기
- 삼성 가우스: 용어 명시, 단계적 접근과 도메인 지식을 사용하는 마케팅 작업
- Gemini: 페르소나 제한과 구체적인 시나리오를 사용하는 창의 작업

영상과 음악 생성에서는 같은 `분위기`라는 표현이 서로 다른 입력 정보로 이어집니다. 영상은 효과·카메라 위치·구도와 움직임 순서가 필요했고, 음악은 장르·악기·템포와 사운드 밀도가 필요했습니다.

![Sora와 Udio 사례까지 확장한 프롬프트 팁 분류](assets/projects/prombank/prototype-tips-categories.jpg)

| 콘텐츠 요소 | 넓은 요청의 문제 | 템플릿에서 분리한 정보 |
|---|---|---|
| 인물 이미지 | `영화 같은 분위기`가 구도와 조명을 모델에 맡김 | 표정, 시선, 카메라 거리, 조명, 색감, 고정 대상 |
| 영상 모션 | `놀라서 뒤돌아본다`의 동작 순서가 바뀜 | 움직일 대상, 시작 상태, 순서, 속도, 종료 상태, 고정 배경 |
| TTS | `슬프게`의 강도가 장면마다 달라짐 | 감정 강도, 발화 속도, 강조어, 문장 사이 정적 |
| 효과음 | 화면 사건과 소리의 시작점이 어긋남 | 발생 원인, 시작 시점, 길이, 거리, 잔향 |
| 배경음악 | 분위기만 맞고 대사와 충돌함 | 장르, 템포, 악기 밀도, 대사 구간 음역, 전환 시점 |

새로운 모델이 나오더라도 콘텐츠 제작자가 확인해야 할 입력과 품질 요소가 남도록 분류했습니다.

## 5. 사례 수집: 성공 결과보다 수정 경로를 먼저 물었습니다

학회 구성원들이 생성형 AI를 활용하며 남긴 프롬프트, 결과 이미지·영상·음성과 원하는 결과에 도달하기까지의 수정 과정을 수집했습니다.

처음에는 잘 나온 결과와 최종 프롬프트를 받으려 했습니다. 그러나 최종 문장만 보면 원래 무엇이 잘못됐는지, 어떤 조건이 결과에 영향을 주었는지 알 수 없었습니다. 그래서 사례를 요청할 때 다음 질문을 함께 확인했습니다.

1. 처음 만들고자 했던 콘텐츠와 장면은 무엇이었는가
2. 첫 결과는 의도와 어떻게 달랐는가
3. 어느 표현이나 조건을 수정했는가
4. 수정 뒤 좋아진 요소와 여전히 남은 문제는 무엇인가
5. 실제 콘텐츠에 사용하려면 어떤 추가 편집이 필요한가

> **영상 생성 사례 기록 예시**
>
> **목표**
> 한 인물이 놀란 뒤 화면 오른쪽을 천천히 바라보는 짧은 리액션
>
> **첫 결과**
> 눈, 고개와 몸이 동시에 움직였고 배경까지 흔들렸습니다.
>
> **수정**
> 눈동자 이동 → 짧은 정지 → 작은 고개 회전으로 순서를 나누고, 카메라·몸통·배경 고정을 별도로 적었습니다.
>
> **남은 검수**
> 얼굴과 의상이 첫 프레임에서 유지되는지, 다음 컷과 연결할 종료 상태가 있는지 확인합니다.

이 기록을 통해 생성 실패를 `모델이 이상했다`는 한 문장으로 끝내지 않고, 다시 돌아갈 입력 단계와 수정 대상을 구분할 수 있었습니다.

### 이미지 생성에서 반복된 문제

- 같은 인물의 얼굴·헤어·의상이 결과마다 달라짐
- 카메라 거리와 시선이 장면 의도와 다름
- 배경 확장 중 새로운 인물과 사물이 생성됨
- 손·소품의 수와 위치가 불안정함
- 분위기는 자연스럽지만 앞뒤 컷의 광원과 색온도가 이어지지 않음

### 영상 생성에서 반복된 문제

- 움직일 인물만 지정했지만 카메라와 배경까지 흔들림
- 여러 동작의 순서가 바뀌거나 동시에 발생함
- 발화하지 않는 인물이 함께 입을 움직임
- 첫 프레임의 얼굴·의상·공간이 영상 중 변형됨
- 개별 동작은 자연스럽지만 편집할 수 있는 종료 상태가 없음

### 음성·사운드에서 반복된 문제

- 감정과 발화 속도가 장면의 길이와 맞지 않음
- 같은 캐릭터의 음색과 연기 강도가 대사마다 달라짐
- 효과음의 발생 시점과 화면의 사건이 어긋남
- BGM의 악기 밀도가 높아 대사 전달을 방해함
- 짧은 전환 뒤 긴 잔향이 남아 다음 장면을 덮음

## 6. 넓은 표현과 구조화된 입력을 비교했습니다

같은 제작 목적에서 프롬프트의 표현과 조건을 달리해 결과를 비교했습니다. 목표는 가장 긴 프롬프트를 찾는 것이 아니라, 결과를 크게 바꾸는 정보와 실패 뒤 수정할 위치를 찾는 것이었습니다.

### 인물 이미지

`영화 같은 분위기의 긴장한 인물`처럼 넓은 표현을 넣은 결과와 아래처럼 조건을 나눈 결과를 비교했습니다.

```text
사용 목적: 대화 장면에서 압박을 느끼는 인물의 미디엄 클로즈업
표정: 입은 닫고 눈썹과 시선만 긴장
시선: 카메라가 아니라 화면 오른쪽의 상대를 봄
카메라: 눈높이, 미디엄 클로즈업
조명: 화면 왼쪽 위의 부드러운 주광원
색감: 저채도 중성 톤
고정: 얼굴·헤어·의상과 배경 구조 유지
금지: 임의 텍스트, 액세서리 추가, 카메라 틸트
```

구조화된 입력은 표정이 틀리면 표정 조건으로, 인물 위치가 틀리면 카메라·구도 조건으로 돌아갈 수 있게 하는 작업 기록입니다.

### 영상 모션

`인물이 놀라 뒤를 돌아본다`를 다음처럼 동작 단위로 분해했습니다.

1. 카메라와 몸통은 고정합니다.
2. 눈동자가 먼저 화면 오른쪽으로 이동합니다.
3. 짧게 정지한 뒤 고개가 같은 방향으로 작게 회전합니다.
4. 눈은 조금 커지되 입과 의상은 움직이지 않습니다.
5. 배경과 조명은 바꾸지 않습니다.

이 사고방식은 카카오엔터테인먼트 숏애니 제작에서 `고정`, `움직임`, `금지 조건`을 제어 단위로 나누는 Layer-in-Layer로 발전했습니다.

### TTS와 사운드

TTS에서는 `슬프게 읽어줘`보다 감정 강도, 발화 속도, 강조할 단어와 문장 사이 정적을 나눴습니다. 효과음과 BGM은 분위기뿐 아니라 발생 시점, 길이, 템포, 악기 밀도와 대사 구간의 음역을 함께 비교했습니다.

> **비교에서 얻은 결론**
>
> 사용자가 자기 장면에 맞게 바꿀 정보와 결과를 지키기 위해 고정할 조건이 분리돼 있을 때 다시 쓰기 쉬웠습니다.

## 7. 재사용 가능한 템플릿 구조

사례를 그대로 게시하면 원래 작성자의 장면에서는 작동해도 다른 사용자가 무엇을 바꿔야 하는지 알기 어렵습니다. 그래서 게시 단위를 다음 네 칸의 제작 기록으로 정리했습니다.

실제 운영에서는 네 칸을 더 세분화해 다음 정보를 함께 기록했습니다.

| 필드 | 기록 내용 | 사용자가 얻는 정보 |
|---|---|---|
| 사용 목적 | 콘텐츠 유형과 장면의 기능 | 자신의 작업과 가까운 사례인지 판단 |
| 변경 정보 | 인물, 표정, 시선, 카메라, 장소, 길이 | 자기 작업에 맞게 교체할 항목 |
| 고정 조건 | 얼굴, 의상, 배경, 금지 변형, 출력 형식 | 결과가 흔들리지 않게 유지할 항목 |
| 결과 예시 | 입력과 연결된 실제 결과 | 문장이 어떤 시각·음성 결과로 이어졌는지 확인 |
| 수정 과정 | 실패 요소, 바꾼 조건과 결과 변화 | 다음 시도에서 돌아갈 위치 |
| 사람의 검토 | 사실, 저작권, 브랜드, 인물 동일성 | 생성 뒤 승인 책임이 남는 항목 |

프롬프트 원문은 템플릿의 일부일 뿐입니다. 결과 이미지나 영상, 수정 전후와 검토 기준이 함께 있어야 다른 사람이 같은 판단을 반복할 수 있다고 보았습니다.

## 8. 프로토타입에서 운영 서비스로

프로토타입에는 홈, 검색, 프로필, 하이라이트, 뉴스, 팁, 포럼과 메뉴·연락처 구조를 설계했습니다. 화면을 만든 뒤에는 콘텐츠를 계속 추가하면서 실제 분류가 축적을 견디는지 확인했습니다.

![프롬프트 팁·뉴스·포럼과 소셜 공유를 연결한 하단 구조](assets/projects/prombank/prototype-footer.jpg)

운영하면서 다음 기준을 적용했습니다.

- 제목만 보고도 작업 목적과 출력 형식을 알 수 있게 했습니다.
- 같은 문장의 중복보다 결과와 수정 근거가 다른 사례를 우선했습니다.
- 동일한 목적의 사례는 콘텐츠 요소와 사용 상황으로 묶었습니다.
- 모델명은 기록하되 템플릿의 핵심을 특정 버전에만 의존하지 않게 했습니다.
- 최종 결과만 좋은 사례보다 실패 원인과 수정 조건이 분명한 사례를 보존했습니다.
- 새 모델과 기능이 나오면 기존 분류에서 어떤 항목이 달라지는지 함께 확인했습니다.

> **운영 중 확인한 차이**
>
> 데모는 화면이 한 번 정상적으로 동작하면 끝날 수 있습니다. 운영 서비스는 새 콘텐츠가 들어올 때마다 제목, 분류, 중복과 품질 기준을 다시 확인해야 합니다.
>
> 422개라는 숫자는 프롬프트의 효과를 증명하는 지표가 아니라, 같은 정보 구조로 콘텐츠를 반복해서 정리하고 운영한 규모를 보여주는 기록입니다.

## 9. MVP 지표와 해석 범위

단과대학을 대상으로 MVP를 공개한 뒤 첫 4주 동안 고유 방문자 1,311명, 방문 세션 3,285회와 평균 세션 시간 2분 55초를 확인했습니다.

이 지표는 방문 규모와 탐색 행동을 보여줍니다. 템플릿 복사 이후의 생성 성공률, 수정 횟수와 콘텐츠 완성률은 당시 분석 범위에 포함하지 않았습니다.

확인할 수 있는 범위는 다음과 같습니다.

- 단과대학 사용자에게 생성형 AI 활용 사례를 찾고 공유하려는 관심이 있었습니다.
- 고유 방문자 수보다 많은 세션이 발생해 여러 콘텐츠를 반복 탐색할 가능성을 확인했습니다.
- 단순 방문 직후 이탈만으로 설명하기 어려운 평균 세션 시간을 기록했습니다.
- 목적별 템플릿과 활용 사례에 대한 초기 수요를 확인했습니다.

운영 지표를 확장한다면 `템플릿 열람 → 복사 → 변수 수정 → 실행 결과 기록 → 재사용` 흐름을 기준으로 실제 실행 전환율, 수정 횟수와 콘텐츠 완성률을 함께 봐야 합니다.

## 10. 이후 프로젝트로 이어진 기준

프롬뱅크에서 시작한 입력 구조화 방식은 숏애니, Antiframe과 AI 드라마의 제작 기준으로 이어졌습니다.

### 웹툰 AI 숏애니메이션

영상 프롬프트에서 움직일 대상·동작 순서와 고정할 배경·카메라를 분리한 경험이 Layer-in-Layer로 구체화됐습니다. 원작 보존, 첫 프레임, 모션, TTS·사운드의 통과 기준을 제작 기록으로 남겼습니다.

### Antiframe

한 프롬프트 안에서 바꿀 정보와 유지할 조건을 나눈 방식을 프로젝트 전체로 확장했습니다. 사용자의 자연어 요청을 변경할 장면·필드와 보존할 결과로 구조화하고, 필요한 부분만 재실행하도록 구현했습니다.

### AI 드라마

텍스트만으로 해결할 수 없는 구도 문제는 스케치로, 인물과 공간의 반복 설명은 캐릭터 팩·공간 팩으로 분리했습니다. 실패 원인을 인물·공간·구도·모션으로 나누어 해당 입력으로 돌아갑니다.

각 프로젝트는 `더 좋은 한 번의 생성`보다 `다음 제작자가 같은 판단을 반복할 수 있는 구조`를 목표로 합니다.

## 11. 운영 이후 정리한 개선안

프롬뱅크 운영 경험을 바탕으로 템플릿 수보다 실행과 수정 이력을 먼저 관리하도록 개선안을 정리했습니다.

1. 모델명뿐 아니라 버전·생성 날짜·입력 이미지와 시드 등 재현 조건을 기록합니다.
2. 템플릿별 열람·복사·수정·실행·재사용 단계를 측정합니다.
3. 원문과 수정본의 차이를 `인물`, `구도`, `모션`, `음성`, `사운드` 필드로 비교합니다.
4. 결과의 실패 유형과 수정 비용을 태그로 연결합니다.
5. 저작권·개인정보·브랜드·사실성 검수 책임을 템플릿에 포함합니다.
6. 모델 업데이트 뒤 동일 입력의 결과 변화를 회귀 테스트합니다.
7. 조직에서 승인한 템플릿과 개인 사례를 구분하고 변경 이력을 남깁니다.

새로운 AI 도구를 실제 제작 현장에 적용할 때 어떤 입력과 검수 기준이 반복 가능한지를 관리하기 위한 개선안입니다.

## 12. 이 경험이 남긴 기준

프롬뱅크를 만들기 전에는 좋은 결과를 얻는 프롬프트를 찾는 일이 중요하다고 생각했습니다. 운영 뒤에는 좋은 결과 하나보다 `왜 작동했는지`, `다른 장면에서는 무엇을 바꿔야 하는지`, `실패하면 어느 조건으로 돌아갈지`를 설명할 수 있는 기록이 더 중요하다고 보게 됐습니다.

이 기준은 숏애니의 Layer-in-Layer, Antiframe의 부분 재실행과 AI 드라마의 캐릭터·공간·구도 팩으로 이어졌습니다. 프롬뱅크의 핵심 산출물은 422개의 문장만이 아니라, 생성형 AI의 시행착오를 다음 제작자가 사용할 수 있는 구조로 바꾸고 이를 실제 서비스로 운영한 경험입니다.
