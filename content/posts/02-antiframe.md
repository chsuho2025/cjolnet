## 제품 한 줄 정의

Antiframe은 ==대본을 넣으면 영상 초안을 만들고, 필요한 부분만 말로 고쳐 완성하는 웹 기반 영상 제작 도구==입니다.

숏애니 제작에서 여러 생성 도구를 오가며 같은 정보를 반복 입력하고, 한 장면의 오류 때문에 전체 공정을 다시 실행하는 문제를 경험했습니다. 이 개인 프로젝트에서는 그 제작 경험을 하나의 제품 흐름으로 바꿨습니다.

![Antiframe 랜딩 화면](assets/projects/antiframe/landing.png)

### 제작자 관점에서 세운 제품 가설

`생성 품질이 더 좋은 모델`만 제공하면 제작 속도가 빨라질 것이라는 가설에서 출발하지 않았습니다. 실제 병목은 결과가 나온 뒤 어느 부분을 승인하고, 무엇을 고치며, 어느 공정부터 다시 실행할지 결정하는 데 있었습니다.

제품 가설을 다음처럼 세웠습니다.

1. 사용자가 타임라인 대신 대본과 장면을 중심으로 작업하면 편집 도구를 몰라도 결과를 검수할 수 있습니다.
2. 전체 영상을 다시 만들지 않고 장면과 변경 필드를 특정하면 제작 비용과 대기 시간을 줄일 수 있습니다.
3. 자연어 요청을 바로 생성 모델에 전달하지 않고 변경 범위로 구조화하면 기존 승인 결과를 보존할 수 있습니다.
4. 자동 생성의 중간 단계는 숨기되, 비용과 방향이 바뀌는 지점에는 Human Checkpoint가 필요합니다.
5. 외부 API가 실패해도 프로젝트 상태와 완료된 결과가 남아야 사용자가 작업을 이어갈 수 있습니다.

이 가설은 화면 설계, 데이터 구조, API 분리와 렌더 워커 운영 기준에 동일하게 적용했습니다.

## 1. 해결하려 한 제작 문제

기존 AI 영상 제작에서는 대본, 음성, 이미지, 영상과 편집 도구가 분리되어 있었습니다. 사용자는 각 도구의 용어와 입력 형식을 익히고, 앞 단계의 결과를 다음 단계에 다시 입력해야 했습니다.

실제 제작에서 더 큰 문제는 생성 자체보다 다음 세 가지였습니다.

- 작업이 어디까지 진행됐는지 추적하기 어렵습니다.
- 한 장면이 잘못되면 무엇을 다시 만들어야 하는지 알기 어렵습니다.
- 자동 생성과 제작자의 판단이 필요한 지점이 구분되지 않습니다.

Antiframe은 이 문제를 `대본 → 영상 초안 → 장면 검토 → 필요한 장면 수정 → 최종 영상`이라는 작업 흐름으로 재구성했습니다.

> 제품의 중심을 생성 기능의 수가 아니라, 제작자가 결과를 확인하고 다음 판단을 내리는 순서에 두었습니다.
>
> 사용자가 `다시 만들어줘`라고 말했을 때 시스템이 전체 영상을 지우는 대신, 어떤 장면의 어떤 필드가 바뀌고 무엇은 유지되는지를 먼저 보여주는 것이 핵심이었습니다.

### 문제를 기능 요청이 아니라 작업 손실로 정의했습니다

- 같은 대본과 스타일 정보를 여러 서비스에 반복 입력하는 시간
- 생성 결과의 버전과 선택 이유가 남지 않아 다시 비교하는 시간
- 한 장면의 오류 때문에 음성·이미지·렌더까지 다시 실행하는 비용
- 생성 중 화면을 닫았을 때 작업 상태를 잃는 위험
- API 오류 문구를 사용자가 해석해야 하는 인지 부담
- 최종 렌더와 웹 서비스의 실행 환경이 달라 발생하는 운영 복잡성

따라서 MVP의 범위를 `AI가 영상을 만들어주는 기능`이 아니라 **한 프로젝트가 중단 없이 다음 상태로 이동하고, 사용자가 필요한 장면만 고칠 수 있는 제작 시스템**으로 잡았습니다.

### 핵심 사용자를 좁힌 이유

초기 타깃은 정보성 설명 영상을 만들고 싶지만 편집 타임라인과 생성 도구를 모두 배우기 어려운 개인 제작자입니다. 역사·경제·정책·과학·건강·트렌드처럼 대본의 논리 순서가 중요하고, 한 장면씩 화면 자료를 연결할 수 있는 콘텐츠를 우선했습니다.

영화·드라마처럼 캐릭터와 공간의 강한 연속성이 필요한 장르를 처음부터 자동화 범위에 넣지 않았습니다. 장르마다 필요한 제작 기준이 다르기 때문에, 설명형 콘텐츠에서 대본 구조화·자료 선택·부분 수정·최종 조립이라는 공통 파이프라인을 먼저 검증했습니다.

## 2. 기능보다 먼저 제품 언어를 정했습니다

사용자에게 `storyboard`, `asset`, `TTS`, `render` 같은 내부 용어를 그대로 보여주지 않았습니다. 제작 프로그램에 익숙하지 않은 사용자도 다음 행동을 이해하도록 문구를 바꿨습니다.

- storyboard → **영상 초안**
- cut → **장면**
- asset → **화면 또는 영상 자료**
- TTS → **내레이션 또는 목소리**
- render → **최종 영상 만들기**
- failed → **오류 상태와 다음 행동**

이 기준은 화면 카피에만 적용되지 않습니다. 내부 상태가 복잡해져도 사용자는 현재 해야 할 일 하나를 이해할 수 있어야 한다는 제품 원칙입니다.

### 내부 상태와 사용자 언어를 분리했습니다

개발 시스템에는 `preparing_storyboard`, `generating_assets`, `ready_to_render`, `rendering`, `completed`, `failed` 같은 상태가 필요합니다. 하지만 사용자가 이 상태명을 이해해야 작업을 이어갈 수 있다면 제품의 내부 구조를 사용자에게 전가하게 됩니다.

화면에서는 다음처럼 행동으로 번역했습니다.

- preparing_storyboard → 영상 초안 만드는 중
- storyboard_ready → 초안 준비됨
- generating_assets → 장면 만드는 중
- ready_to_render → 완성 준비됨
- rendering → 최종 영상 만드는 중
- completed → 완성됨
- failed → 오류 내용과 다시 시도할 단계

상태 배지는 시스템의 진행률을 보여주되, 주요 버튼은 `다음 상태 이름`이 아니라 `사용자가 하게 될 일`을 표시했습니다.

### 한 화면에는 하나의 세부 판단만 배치했습니다

초기 화면에서는 여러 제작 설정과 진행 단계를 동시에 보여주면 기능은 많아 보이지만, 사용자는 지금 무엇을 결정해야 하는지 찾기 어려웠습니다. 전공정은 한 페이지에 형식, 주제, 키워드, 대본 중 하나만 보여주고 이전·다음으로 이동하도록 구성했습니다.

후공정도 장면 검토, 배경음악, 자막, 최종 영상 만들기를 한 화면에 모두 쌓지 않고 현재 작업 단위에 맞춰 이동하게 했습니다. 화면 수를 줄이는 것보다 **한 화면에서 경쟁하는 판단의 수를 줄이는 것**을 우선했습니다.

## 3. 전공정: 제작 조건을 한 번만 입력합니다

처음부터 모든 설정을 한 화면에 펼치지 않았습니다. 사용자는 다음 순서로 영상의 조건을 정합니다.

1. 세로형 숏폼 또는 가로형 롱폼 선택
2. 영상의 주제와 카테고리 입력
3. 설명에 필요한 키워드 정리
4. 직접 작성하거나 보조받은 대본 확인
5. 내레이션 목소리 선택

![한 화면에서 하나의 판단만 하도록 구성한 영상 형식 선택 화면](assets/projects/antiframe/format-select.png)

![대본의 성격에 맞는 내레이션을 고르는 화면](assets/projects/antiframe/voice-select.png)

형식과 음성처럼 결과 전체에 영향을 주는 결정은 사용자에게 남기고, 대본을 장면으로 나누거나 반복 입력을 변환하는 작업은 시스템이 이어서 수행하도록 설계했습니다.

### 형식 선택이 뒤 단계에 전달하는 값

숏폼과 롱폼은 화면비만 다르지 않습니다.

- 숏폼은 장면 길이와 첫 정보 도달 시간을 짧게 잡습니다.
- 롱폼은 설명의 논리 단위와 호흡을 더 길게 유지합니다.
- 형식에 따라 장면 수, 자막 길이, 자료 화면의 정보 밀도와 최종 렌더 설정이 달라집니다.
- 사용자가 입력한 대본의 말투와 주장을 더 자극적으로 바꾸지는 않습니다.

형식은 모든 공정이 참조하는 프로젝트 값으로 저장하고, 장면을 생성할 때마다 다시 선택하게 하지 않았습니다.

### 대본을 대신 쓰는 기능과 대본을 바꾸는 기능을 구분했습니다

사용자가 직접 쓴 대본은 원래 주장과 순서를 보존합니다. 시스템은 영상에 맞게 장면을 나누고 문장을 읽기 좋게 정리하지만, 근거 없는 사례·수치·강한 주장을 추가하지 않도록 했습니다.

주제와 키워드만 입력한 경우에는 초안 작성을 보조할 수 있지만, 이 결과도 사용자가 대본 단계에서 확인한 뒤 후공정으로 넘어갑니다. 생성된 텍스트를 바로 영상 제작 비용이 드는 단계로 보내지 않는 Human Checkpoint입니다.

## 4. 후공정: 대본을 검수 가능한 장면으로 바꿉니다

대본 입력이 끝나면 별도의 `생성 시작` 버튼을 반복해서 누르게 하지 않습니다. 시스템은 대본을 장면 단위로 나누고, 각 장면에 필요한 정보를 묶습니다.

- 장면이 영상에서 담당하는 역할
- 화면에 전달해야 할 핵심 정보
- 내레이션 원문과 실제 발음용 문장
- 이미지·영상 자료를 찾거나 생성하기 위한 시각 정보
- 장면의 길이와 전환 방식
- 현재 생성 상태와 다시 실행할 수 있는 범위

사용자는 완성된 초안을 기준으로 장면을 검토합니다. 제작 파이프라인의 내부 단계가 아니라, **어느 장면이 의도와 다른지**를 보게 하는 것이 목적입니다.

### 대본을 장면으로 나누는 기준

고정 글자 수로만 나누지 않고 의미 전환을 먼저 찾았습니다.

- 주제 설정
- 원인과 결과
- 서로 다른 주장이나 대비
- 사례와 근거
- 해결 방법
- 결론과 다음 행동

각 장면은 원문 순서를 유지하며 하나의 주장에 집중합니다. 짧은 문장 두 개라도 의미가 다르면 합치지 않고, 한 주장이 길면 3~7초 내레이션 단위로 나눕니다. 장면 제목은 `알아보기`, `설명하기` 같은 반복적인 작업명이 아니라 해당 장면의 원인·변화·결과를 드러내는 명사형으로 생성합니다.

### 한 장면이 보유하는 실제 제작 정보

- `source_text`: 원본 대본에서 이 장면이 담당하는 범위
- `narration`: 화면 자막과 사용자 검수에 쓰는 문장
- `tts_script`: 숫자·영어·단위를 자연스럽게 읽도록 바꾼 음성 전용 문장
- `subtitle_segments`: 한 줄 자막으로 순차 표시할 의미 단위
- `scene_description`: 장면이 전달해야 할 구체적인 시각 정보
- `asset_function`: 도입·문제·과정·근거·대비·결과·분위기·연결 중 역할
- `asset_subject / action / setting`: 자료 검색에 필요한 대상·행동·공간
- `scene_candidates`: 실사 영상, 이미지, AI 생성 중 가능한 자료 후보
- `effect_type`: 고정, 줌, 좌우·상하 패닝 등 정지 자료의 움직임
- `duration_sec`: 내레이션과 자료가 점유할 시간

사용자는 이 필드명을 볼 필요가 없지만, 시스템은 장면을 다시 만들 때 무엇을 유지하고 무엇을 바꿀지 판단하기 위해 구조화된 값이 필요합니다.

### 화면 자료는 ‘촬영 지시’가 아니라 ‘찾을 수 있는 자료’로 설계했습니다

설명형 콘텐츠에서 모든 장면을 AI로 생성하면 비용이 증가하고 실제 자료가 필요한 내용의 신뢰감이 떨어질 수 있습니다. 반대로 추상적인 문장을 그대로 스톡 검색하면 `business`, `technology`, `future` 같은 모호한 결과가 반복됩니다.

그래서 시각 계획을 아카이브 편집자의 관점으로 바꿨습니다.

1. 장면의 기능을 도입·과정·근거·대비·결과 중 하나로 정합니다.
2. 화면에 실제로 보일 대상, 행동과 공간을 추출합니다.
3. `hands typing laptop office`, `team reviewing dashboard meeting room`처럼 검색 가능한 영어 조합으로 변환합니다.
4. 현실 장면은 움직임이 있는 스톡 비디오를 우선합니다.
5. 영상 결과가 과하게 복잡하거나 참고 이미지가 중요한 경우 스톡 이미지를 사용합니다.
6. 역사·추상 개념·도표처럼 찾기 어려운 장면은 AI 이미지로 전환합니다.
7. 움직임 자체가 설명에 필요하고 스톡으로 찾기 어려울 때만 AI 비디오를 사용합니다.

인접 장면에 같은 사무실·노트북 화면이 반복되지 않도록 대상·행동·공간 중 하나 이상을 바꾸는 규칙도 포함했습니다.

## 5. 자연어 수정은 장면 선택부터 시작합니다

영상 전체를 채팅으로 다시 만드는 방식은 통제 범위가 불명확합니다. Antiframe의 수정 흐름은 먼저 장면을 고르고, 그 장면 안에서 바꿀 요소를 해석합니다.

예를 들어 사용자가 `두 번째 장면의 설명을 더 쉽게 하고, 화면은 수치가 보이는 자료로 바꿔줘`라고 입력하면 다음처럼 분리합니다.

1. 대상은 두 번째 장면으로 고정합니다.
2. 내레이션 문장과 화면 자료가 변경 대상입니다.
3. 다른 장면, 선택한 목소리와 전체 영상 형식은 유지합니다.
4. 변경된 요소만 다시 만들고 결과를 비교합니다.

요청이 `더 좋게 바꿔줘`처럼 넓으면 즉시 전체를 수정하지 않습니다. 더 쉽게, 더 역동적으로, 더 차분하게, 화면 위주로 같은 선택지를 제시하거나 추가 질문으로 범위를 좁힙니다.

[[antiframe-change-scope]]

### 자연어를 프리셋으로 축소하지 않았습니다

추천 버튼은 입력을 돕는 약한 힌트일 뿐입니다. `더 쉽게`, `더 차분하게` 같은 몇 가지 프리셋 문장을 반환하는 시스템으로 만들지 않았습니다. 실제 API는 현재 장면의 내레이션, 발음용 문장, 화면 설명, 이미지·영상 검색 방향과 움직임을 함께 읽고 사용자의 문장을 직접 해석합니다.

요청의 성격에 따라 다음 필드 조합이 달라집니다.

- 발음 요청은 화면 자막을 유지하고 `tts_script`만 바꿉니다.
- 시각 자료 요청은 내레이션을 유지하고 자료 검색 방향과 움직임만 바꿉니다.
- 표현을 쉽게 해달라는 요청은 원래 의미와 사실 범위를 유지한 채 내레이션과 음성을 바꿉니다.
- 시각 방향이 바뀌어 기존 자료가 맞지 않을 때만 해당 장면의 자료 선택을 초기화합니다.
- 수정 응답에는 실제로 바뀐 항목만 설명하고, 유지한 요소를 바꿨다고 말하지 않습니다.

> **자연어 요청 처리 예시**
>
> **사용자 요청**
> “두 번째 장면의 설명을 더 짧고 쉽게 바꿔줘. 지금 화면 자료는 그대로 두고.”
>
> **장면 범위**
> 선택한 두 번째 장면만 대상으로 삼습니다.
>
> **변경 필드**
> 화면에 표시할 자막 문장과 실제 발음용 `tts_script`를 함께 수정합니다.
>
> **보존 필드**
> 승인한 화면 자료, 장면 순서, 목소리, 배경음악과 다른 장면은 유지합니다.
>
> **재실행 대상**
> 해당 장면의 TTS와 최종 렌더 구간만 다시 만듭니다.

### 수정 결과를 바로 덮어쓰지 않는 이유

수정 API의 결과는 구조화된 변경안입니다. 장면에 적용하기 전 현재 값과 비교해 어떤 필드가 달라졌는지 확인합니다. 화면 자료가 바뀌면 자료를 다시 찾거나 생성해야 하고, 내레이션이 바뀌면 TTS와 자막 세그먼트를 다시 만들어야 합니다.

이 비교가 없으면 `문장을 조금 쉽게`라는 요청으로 영상 자료와 최종 렌더까지 불필요하게 초기화될 수 있습니다. 자연어 UX 뒤에는 변경 범위를 통제하는 상태 로직이 필요했습니다.

| 요청 문장 | 시스템이 먼저 확인할 범위 | 변경 | 보존 |
|---|---|---|---|
| “발음만 고쳐줘” | 선택 장면·발음 대상 단어 | `tts_script`, 해당 음성 | 화면 자막·자료·다른 장면 |
| “이 문장을 쉽게 바꿔줘” | 원래 의미를 보존할지 확인 | 내레이션·화면 자막·음성 | 장면 자료가 계속 맞으면 유지 |
| “화면만 다른 자료로 바꿔줘” | 내레이션과 새 자료의 일치 | 시각 설명·검색/생성 요청 | 대본·목소리·앞뒤 장면 |
| “전환을 더 차분하게” | 장면 하나 또는 연결 구간 | 전환·모션 설정 | 대본·자료·음성 |
| “두 번째 장면을 다시 구성해줘” | 장면 전체 변경임을 고지 | 해당 장면의 텍스트·자료·음성 | 프로젝트 설정·나머지 장면 |

[[antiframe-demo]]

위 데모는 외부 생성 API와 저장 기능을 제거한 포트폴리오용 재현입니다. 실제 제품에서 중요하게 설계한 **장면 선택 → 자연어 요청 → 변경 요소 확인 → 해당 범위만 재실행**의 상호작용을 직접 확인할 수 있습니다.

## 6. Human Checkpoint를 남긴 기준

자동화는 버튼을 없애는 것이 아니라, 불필요한 판단을 없애는 일로 정의했습니다.

### 시스템이 자동으로 이어가는 단계

- 대본을 장면 단위로 구조화
- 앞 단계의 입력값을 다음 단계 형식으로 변환
- 장면별 생성 상태와 결과 저장
- 완료된 단계는 유지하고 필요한 단계만 재실행
- 최종 영상 제작에 필요한 파일과 정보를 조립

### 사용자가 확인하는 단계

- 영상 형식과 전달 목적
- 대본의 내용과 목소리
- 장면 구성이 의도와 맞는지
- 자연어 수정 요청의 대상과 범위
- 배경음악·자막과 최종 제작 실행

이 구분은 비용과 품질을 동시에 다룹니다. 생성 비용이 드는 변경은 사용자의 의도를 확인한 뒤 실행하고, 단순한 데이터 변환과 상태 연결은 자동화합니다.

### Human Checkpoint를 판단한 세 가지 기준

1. **방향성:** 콘텐츠의 주장, 포맷, 목소리처럼 결과 전체의 인상을 바꾸는가
2. **비용:** 외부 생성 API나 최종 렌더처럼 실행 비용과 대기 시간이 발생하는가
3. **비가역성:** 기존 승인 결과를 덮어쓰거나 다른 단계의 결과를 오래된 상태로 만드는가

세 항목 중 하나라도 크면 사용자 확인을 남겼습니다. 반대로 장면 번호 계산, 자막 세그먼트 변환, 완료된 파일 경로 연결처럼 시스템이 정확히 수행할 수 있는 작업은 자동으로 이어갔습니다.

### 진행 상태를 프로젝트에 귀속했습니다

생성 중인 요청을 브라우저 화면에만 보관하면 사용자가 이동하거나 새로고침할 때 현재 상태를 잃습니다. 작업 상태, 완료 결과와 오류를 프로젝트에 저장하고, 다시 열었을 때 마지막으로 이어갈 수 있는 단계로 이동하게 했습니다.

최종 영상이 만들어진 뒤 대본이나 장면이 수정되면 기존 MP4를 즉시 삭제하지 않습니다. 기존 결과는 기록으로 남기되 현재 프로젝트와 맞지 않는 상태임을 표시하고, 재제작이 필요하다는 다음 행동을 제공합니다.

## 7. 실패를 막다른 화면으로 만들지 않았습니다

생성 파이프라인에서는 외부 API, 파일 저장과 렌더 작업이 각각 다른 이유로 멈출 수 있습니다. 처음부터 모든 오류를 `다시 만들기` 하나로 처리하면 이미 완료된 결과까지 잃고 비용을 반복하게 됩니다.

그래서 실패 상태를 공정과 장면 단위로 기록하고, 돌아갈 수 있는 위치를 분리했습니다.

- 초안 구조 오류 → 대본 분석 단계만 재시도
- 특정 장면 자료 오류 → 해당 장면의 자료만 다시 생성
- 내레이션 발음 오류 → 발음용 문장과 음성만 수정
- 최종 영상 오류 → 장면 결과는 유지하고 최종 제작만 재시도
- 수정 후 최종 영상이 오래된 상태 → 기존 결과를 폐기하지 않고 재제작 필요 상태 표시

오류 메시지에는 내부 시스템명보다 사용자가 다음에 할 수 있는 행동을 표시했습니다. 운영 기록에는 실패 원인을 남기되, 사용자 화면에서는 `어떤 장면을 다시 만들면 되는지`가 먼저 보이도록 했습니다.

> **오류 화면에서 전달해야 할 정보**
>
> `생성에 실패했습니다`라는 문장만 보여주지 않습니다. 어떤 장면의 어느 단계에서 멈췄는지, 이미 완료된 대본·자료·음성은 유지되는지, 다시 시도하면 비용이 발생하는 범위가 어디인지 함께 표시합니다.
>
> 운영자가 확인할 오류 코드와 사용자가 이해할 다음 행동은 분리합니다. 내부 로그는 원인을 추적하기 위한 것이고, 화면 문구는 작업을 이어가기 위한 것이기 때문입니다.

### 실제로 분리한 실패 구간

- 대본 분석 API의 시간 초과와 잘못된 구조 응답
- 특정 장면의 스톡 검색 결과 없음
- 이미지·영상 생성의 외부 작업 지연
- TTS 발음 오류 또는 음성 파일 저장 실패
- 원격 파일을 렌더 패키지에 모으는 과정의 오류
- 렌더 작업 큐 생성 전 실패
- Mac 렌더 워커가 작업을 수집한 뒤 After Effects 실행 실패
- 큰 MP4 업로드와 저장 용량 제한
- 렌더 완료 후 웹 프로젝트 상태 동기화 실패

각 오류가 같은 `failed` 상태로 보이더라도 운영 로그에는 어느 단계에서 멈췄는지, 어떤 입력과 작업 ID였는지 남겼습니다.

### 재시도 정책

- 네트워크성 오류는 제한 횟수 안에서 자동 재시도합니다.
- 구조가 잘못된 응답은 파싱 실패를 명시하고 원본 프로젝트를 유지합니다.
- 한 장면의 자료 오류는 다른 장면의 완료 상태를 건드리지 않습니다.
- 렌더 실패 기록은 삭제하지 않고 `render_jobs`에 남겨 반복 원인을 추적합니다.
- 실행 중인 렌더만 중복 요청을 막고, 실패 또는 완료 뒤에는 조건에 맞게 다시 실행할 수 있습니다.
- 같은 상태에서 버튼만 반복해서 눌러 비용이 중복되는 경우는 차단합니다.

실패를 숨기지 않고 **다시 실행할 수 있는 단위와 실행하면 안 되는 중복 조건**을 함께 정의했습니다.

## 8. 문서가 코드보다 먼저 바뀌는 운영 방식

Antiframe은 기능을 추가할 때 바로 화면부터 수정하지 않았습니다.

1. 제품 기준 문서에서 사용자 흐름과 문구를 먼저 변경합니다.
2. 바뀐 기준에 따라 화면과 파이프라인을 구현합니다.
3. 구현 후 실제 화면이 기준 문서와 같은지 QA합니다.
4. 스펙이 잘못됐다면 코드에 예외를 더하기 전에 문서를 수정합니다.

이 방식으로 제품 정의, 용어 사전, 페이지 목적, 상태 문구, 오류 처리와 QA 기준을 한 문서에서 관리했습니다. 변경 이력에는 무엇을 고쳤는지만이 아니라 문제가 발생한 조건과 검증 결과를 함께 남겼습니다.

### 관리한 문서의 역할

- **Product Spec:** 제품 정의, 사용자, 용어, 전체 흐름, 페이지 목적과 금지 문구
- **UI/UX 기획서:** 화면별 정보 구조, 상태와 다음 행동
- **API·파이프라인 스펙:** 입력·출력, 오류와 저장 규칙
- **Patch Notes:** 문제 상황, 수정 범위, 코드 변경과 검증 결과
- **운영 문서:** 배포, 렌더 워커, 작업 큐, 저장소와 장애 대응
- **인수 문서:** 서비스를 다른 사람이 실행하고 확인하기 위한 전체 구조

기획 문서와 기술 문서를 분리하면서도 같은 상태명과 제작 흐름을 사용했습니다. 화면에서 `최종 영상 만드는 중`이라고 표시되는 상태가 작업 큐의 어떤 값과 연결되는지 추적할 수 있도록 했습니다.

### QA를 사용자 행동과 운영 상태로 나눴습니다

사용자 QA에서는 시작부터 완성 영상 다운로드까지 막히는 버튼, 잘못된 다음 경로, 모바일 줄바꿈과 오류 문구를 확인했습니다. 운영 QA에서는 프로젝트 상태, Storage 파일, render job, worker claim, After Effects 출력과 최종 URL 동기화를 확인했습니다.

화면에서 완료처럼 보여도 파일이 없을 수 있고, 파일이 완성돼도 프로젝트 상태가 갱신되지 않을 수 있습니다. 따라서 UI 성공 여부와 실제 산출물 존재 여부를 별도로 확인했습니다.

## 9. 구현 구조

제품은 Next.js와 TypeScript 기반의 웹 애플리케이션으로 구현했습니다. 제작 흐름을 화면 단위가 아니라 프로젝트 상태로 이어지게 설계하고, 다음 영역을 분리했습니다.

- **전공정 화면:** 형식, 주제, 키워드, 대본과 목소리 입력
- **프로젝트 작업실:** 장면별 초안, 생성 상태와 수정 이력
- **자연어 수정:** 대상 장면과 변경 필드를 구조화
- **생성 API:** 대본 분석, 음성, 화면 자료와 장면 처리
- **최종 제작:** 완료된 장면을 묶어 영상 파일 생성
- **운영·QA:** 중단된 작업, 외부 API 오류와 재시도 기록

외부 서비스를 하나로 고정하지 않고 공정별 역할로 분리했습니다. 텍스트 구조화, 내레이션, 자료 검색·생성, 영상 조립은 각자의 입출력과 실패 상태를 갖습니다. 따라서 한 서비스의 오류가 전체 프로젝트를 처음으로 되돌리지 않도록 했습니다.

### 최종 렌더를 별도 워커로 분리한 결정

초기에는 웹 서버에서 FFmpeg 바이너리로 최종 MP4를 직접 만들려고 했습니다. 하지만 서버리스 배포 환경의 실행 시간, 번들 크기와 바이너리 포함 문제 때문에 안정적으로 운영하기 어려웠습니다.

최종 구조에서는 웹 API가 장면 영상·이미지, 장면별 음성, BGM, 자막, 효과와 렌더 설정을 `render package`로 묶습니다. 패키지를 Storage에 올리고 `render_jobs`에 queued 작업을 생성합니다.

Mac mini의 렌더 워커는 다음 순서로 처리합니다.

1. queued 작업을 조회하고 자신이 처리할 작업을 processing으로 claim합니다.
2. 패키지를 내려받고 작업별 폴더에 해제합니다.
3. 장면 파일, 내레이션, BGM과 자막 정보를 읽습니다.
4. After Effects 스크립트로 컴포지션과 타임라인을 만듭니다.
5. 최종 MP4를 렌더하고 필요한 경우 저장 용량에 맞게 압축합니다.
6. 결과를 Storage에 업로드합니다.
7. render job을 completed로 바꾸고 output URL을 프로젝트에 연결합니다.
8. 실패하면 error message와 worker 정보를 남기고 다시 실행할 수 있게 합니다.

이 구조는 웹 화면과 무거운 미디어 렌더를 분리하고, 작업 큐를 통해 어느 단계가 진행 중인지 추적하게 합니다.

### 렌더 패키지에 포함하는 정보

- 장면 순서와 각 장면의 이미지·영상 유형
- 사용할 파일 또는 원격 자료 URL
- 장면별 길이와 영상 시작 지점
- 장면별 내레이션 파일
- 한 줄씩 표시할 자막 세그먼트
- 줌·패닝 같은 장면 효과
- BGM 파일
- 해상도, 비트레이트와 출력 설정

최종 렌더가 실패해도 장면별 결과를 다시 생성할 필요가 없도록 입력 패키지를 독립된 작업 단위로 만들었습니다.

### 자료 선택과 생성 서비스를 역할로 추상화했습니다

사용자 화면에는 Pexels, Gemini, TTS 공급자와 내부 모델명을 핵심 작업명으로 노출하지 않았습니다. 사용자는 `화면 자료`, `내레이션`, `장면 다시 만들기`를 선택합니다.

공급자가 바뀌어도 제품 흐름을 유지하려면 각 공정이 동일한 역할과 상태를 반환해야 합니다. 그래서 모델 선택보다 장면 결과의 URL, 미디어 유형, 출처, 생성 상태와 재시도 가능 여부를 중심으로 연결했습니다.

## 10. 초기 사용자 검증

초기 사용자 42명이 제품을 사용했고, 설문 응답자 39명 가운데 33명이 지속 사용 의향을 보였습니다.

| 확인 항목 | 결과 | 해석 범위 |
|---|---|---|
| 초기 사용자 | 42명 | 초기 사용 경험을 확보한 규모 |
| 설문 응답 | 39명 | 사용 후 의견을 확인한 표본 |
| 지속 사용 의향 | 33명 | 후속 사용 의사가 있다는 신호 |
| 아직 확인하지 못한 것 | 장기 잔존·유료 전환·제작시간 절감 | 초기 의향을 제품 성과로 과장하지 않음 |

이 수치는 완성된 시장 검증으로 과장하지 않습니다. 초기 단계에서 확인한 것은 다음 두 가지입니다.

1. 편집 타임라인보다 대본과 장면 중심의 흐름을 이해할 수 있는가
2. 전체 재생성보다 필요한 장면만 자연어로 수정하는 방식에 사용 의향이 있는가

사용 과정에서 발견된 혼란은 제품 기준 문서와 화면 문구에 반영했습니다. 특히 사용자가 내부 공정명을 추적해야 했던 화면을 작업 행동 중심으로 바꾸고, 생성 후 다음 버튼을 찾는 단계를 줄였습니다.

### 수치를 해석한 방식

42명의 초기 사용과 39명의 설문은 대규모 정량 검증이 아닙니다. 33명의 지속 사용 의향을 `제품이 완성됐다`는 증거로 사용하지 않고, 제작 흐름을 더 깊게 검증할 근거로 봤습니다.

> **검증 결과를 읽은 방식**
>
> 39명 중 33명의 지속 사용 의향은 `완성된 제품 시장 적합성`을 증명하지 않습니다. 다만 생성 결과를 한 번 보여주는 데모보다, 장면을 검토하고 필요한 부분만 수정하는 흐름에 후속 사용 이유가 있음을 확인한 초기 신호로 해석했습니다.

검증의 초점은 다음과 같습니다.

- 사용자가 `영상 초안`과 `최종 영상`의 차이를 이해하는가
- 어느 장면을 수정해야 하는지 찾을 수 있는가
- 자연어 수정이 전체 영상을 바꾸지 않는다는 신뢰가 생기는가
- 생성 중 기다려야 하는 단계와 직접 행동할 단계를 구분하는가
- 실패 후 다시 시작하지 않고 이어갈 수 있는가

초기 피드백을 통해 생성 버튼을 추가하는 것보다 현재 작업 위치와 다음 행동을 더 명확하게 만드는 수정이 우선이라는 결론을 얻었습니다.

### 다음 검증에서 측정할 항목

- 대본 입력부터 첫 영상 초안 확인까지 걸리는 시간
- 장면 수정 완료까지 필요한 클릭과 자연어 왕복 수
- 전체 재생성 대비 부분 수정으로 절약한 생성 횟수
- 실패 후 같은 프로젝트에서 작업을 재개한 비율
- 자동 추천 자료를 그대로 사용한 비율과 직접 교체한 이유
- 완성 영상 다운로드까지 도달한 비율

지속 사용 의향을 실제 반복 사용과 제작 완료율로 연결하는 것이 다음 단계입니다.

## 11. 숏애니 경험이 제품으로 확장된 지점

숏애니에서는 얼굴·그림체·배경을 레이어로 분리해 움직일 대상만 바꿨습니다. Antiframe에서는 같은 원리를 제작 공정 전체에 적용했습니다.

- 한 화면의 레이어 → 한 프로젝트의 제작 단계
- 움직일 요소 → 사용자가 수정 요청한 장면과 필드
- 보존 요소 → 이미 승인된 다른 장면과 설정
- 실패 원인 진단 → 특정 단계만 재실행하는 상태 구조

Layer-in-Layer가 생성 프롬프트를 통제하는 방식이었다면, Antiframe은 **제작 시스템에서 유지할 것과 다시 만들 것을 분리하는 방식**입니다.

### AI 콘텐츠 제작 직무에서의 의미

Antiframe은 개발 기술을 보여주기 위한 별도 프로젝트가 아닙니다. 콘텐츠 제작자가 반복해서 겪는 판단을 제품 규칙으로 옮긴 작업입니다.

- 좋은 장면을 만드는 기준을 장면 데이터 구조로 변환했습니다.
- 생성 결과 선택을 승인·수정·재시도 상태로 변환했습니다.
- 자연어 연출 요청을 변경 필드와 후속 공정으로 변환했습니다.
- 편집 프로그램에서 수행하던 최종 조립을 렌더 패키지와 워커로 변환했습니다.
- 개인 작업 기록을 제품 스펙·패치 노트·운영 문서로 변환했습니다.

즉 제작 경험이 기획으로, 기획이 구현과 운영으로 이어지는 전체 사이클을 수행했습니다.

## 12. 현재 한계와 다음 개선

현재 제품은 설명형 영상 제작에 맞춰져 있으며 다음 한계가 있습니다.

- 복잡한 캐릭터 연속성과 영화적 공간 연출은 별도 제작 기준이 필요합니다.
- 스톡 자료의 의미 적합성과 저작권 표기를 더 정교하게 검수해야 합니다.
- 자연어 요청이 넓을 때 변경 범위를 확인하는 UX를 더 반복 검증해야 합니다.
- 장면별 품질 점수와 재생성 비용을 한 화면에서 비교하는 기능이 필요합니다.
- 초기 사용자 의향을 실제 완성 영상 수와 재방문으로 연결해야 합니다.
- 렌더 워커의 장시간 작업, 큰 파일 업로드와 장애 복구를 지속적으로 안정화해야 합니다.

다음 AI 드라마 프로젝트에서는 Antiframe의 프로젝트 상태·부분 수정 개념을 Character Pack, Space Pack과 Continuity QC에 적용할 수 있는지 검토합니다. 자동 생성 범위를 넓히기 전에 장르별로 사람이 승인해야 할 기준을 먼저 정의합니다.
